## 2. プロジェクト概要

### 2.1 背景
近年、国内のマッチングアプリ累計利用者数は3,000万人を超えるが、「アプリ疲れ」を理由とする離脱が顕在化している。スワイプ型・即決型の出会い体験は心理的負荷が高く、内向型・派手な婚活に抵抗のある層が、安心して利用できる出会いの場を欠いている状況がある。

一方、街頭・通勤・通学等の生活圏で繰り返し見かける相手と「自然な形でつながる手段」も社会的に消失している。直接的な声かけは現代の安全観・ハラスメント観点から不適切と見なされ、結果として「縁の芽」が日常から失われている。

本プロダクトは、この社会課題に対し、**生活圏での自然な接点を起点に、双方向の合意のもとで段階的に縁を育てる**新しい出会い体験を提供することを目的とする。

### 2.2 プロジェクトの目的
1. **短期目的**: 福岡ハッカソンにおけるプロトタイプ提出と入賞
2. **中期目的**: β版・α拡大版を経た事業化（24ヶ月計画）
3. **長期目的**: 「マッチングアプリ第三の道」としての市場ポジション確立

### 2.3 プロジェクトのスコープ

#### 含むもの（MVP）
- ユーザー登録・プロフィール管理機能
- すれ違い検出データの記録機能（API 側）
- 段階的情報開示機能（4段階）
- 相互合意による早期開示機能
- サイレントリジェクト機能
- 自動拠点保護機能（自宅500m圏）

#### 含まないもの（MVP）
- すれ違いを検出する物理的な仕組み（BLE/GPS）の本格実装 → ハッカソンではシミュレーションで代替
- 通報後のアカウントカウントリセット機能（警告マークのみ）
- give-give（小さな贈り合い）機能（モック表示のみ）
- 課金・決済機能
- 詳細な除外設定（曜日・日付）
- 通知（プッシュ・メール）
- 本人確認・年齢確認

## 3. プロダクト基本情報

### 3.1 プロダクト名
**Meguriai**（めぐりあい）

「巡り会い」に由来する。生活圏で繰り返し接点が生まれ、双方の合意のもとで縁が育つ、というプロダクトのコアコンセプトを体現する。

### 3.2 一行説明
> 同じ生活圏で繰り返し接点が生まれる相手との出会いを、双方の合意のもとで一歩前に進めるマッチングアプリ。

### 3.3 主要なコンセプト
1. **段階的開示**: すれ違い回数に応じて、相手の情報が段階的に開示される
2. **双方向合意**: 詳細プロフィールの開示は、両者の合意があった場合のみ実施
3. **観察非対称を作らない設計**: 場所・時刻情報をユーザーに表示しない
4. **静かな離脱**: サイレントリジェクトで相手を傷つけずに離れられる

## 4. ターゲットユーザーとペルソナ

### 4.1 主要ターゲット
- 20代中盤〜30代後半の独身者
- 職場と自宅の往復で新しい出会いがない層
- 派手な婚活パーティーやスワイプ型アプリに抵抗がある層
- アプローチに受動的な内向型ユーザー

### 4.2 想定ペルソナ
- 同じ生活圏でゆるやかに接点が重なっている相手と、双方の合意ベースで自然に縁を育てていきたい層
- HSP（Highly Sensitive Person）的傾向、もしくは内向型尺度（introversion）が高い層

### 4.3 明示的なターゲット外
- 「今夜すぐ会いたい」即時系のニーズを持つ層
- 数の効率を求める層
- マッチング件数を稼ぐことが目的の層

### 4.4 想定市場規模
- 国内独身者（20-39歳）約 1,300 万人 ※2020年代国勢調査ベース
- マッチングアプリ未利用者比率 約60% → 約 780 万人
- 「派手なアプリに抵抗あり」層 約30% → 約 234 万人
- 利用意向あり 約30% → **想定 TAM 約 70 万人**
- 平均 LTV 1.5万円（月額 1,500円 × 平均 10ヶ月）と仮置きすると、TAM 規模は **約 105 億円**

> 上記はすべて推計値。一次調査による検証は別途実施予定。

## 5. 用語定義

| 用語 | 定義 |
|---|---|
| すれ違い | 両ユーザーが地理的に一定距離内に同時刻に存在した状態 |
| すれ違いカウント | 同一ペアにおける、すれ違い発生の累積回数（同日内重複は1回として丸める） |
| 段階（Lv.） | 開示される情報の段階。Lv.0〜Lv.3 の4段階 |
| アプローチ解禁 | すれ違いカウントが3回に達した時点で、合意のためのインタラクションが可能になる状態 |
| 合意ショートカット | アプローチ解禁後、4回目のすれ違い発生前に双方が合意した場合、詳細プロフィール（Lv.3）を即時開示する機能 |
| 合意の有効期限 | 4回目のすれ違いが発生する時点で合意が未成立の場合、その合意提案は失効する |
| サイレントリジェクト | 相手に通知することなく、ユーザーが当該相手とのカウントを止める機能 |
| 拠点保護 | ユーザーが指定した自宅・拠点から半径500m以内のすれ違いを、自動的にカウント対象外とする機能 |
| 観察非対称 | 一方のユーザーがもう一方の情報のみを蓄積している状態。本プロダクトはこれを構造的に排除する |

## 6. 機能要件

### 6.1 ユーザー管理（FR-USR）

#### FR-USR-01 ユーザー登録
- 匿名セッション方式により、ニックネーム入力のみで利用開始可能
- 登録項目: ニックネーム（必須、40文字以内）、自己紹介サマリー（任意、200文字以内）、詳細プロフィール（任意、2000文字以内）、アイコンURL（任意）
- 登録時にユーザーIDが発行され、クライアント側で保持される

#### FR-USR-02 自宅座標登録
- ユーザーは自宅の緯度経度を任意で登録できる
- 登録方法は手動入力または現在地取得（ブラウザ位置情報API）
- 登録された座標は §6.5 拠点保護機能の判定に使用される
- スキップ可能（その場合、拠点保護は機能しない）

#### FR-USR-03 自分のプロフィール参照
- ユーザーは自身のプロフィール情報を参照できる

### 6.2 すれ違い検出と記録（FR-ENC）

#### FR-ENC-01 すれ違い記録
- ユーザーの現在位置（緯度経度）と、検出された相手ユーザーIDのリストを受け取り、すれ違いとして記録する
- 同日内の重複は1回として丸める（同日丸めルール）
- 自分または相手のいずれかが拠点保護圏内（§6.5）にいる場合は記録しない
- 自分または相手のいずれかがサイレントリジェクト関係にある場合は記録しない

#### FR-ENC-02 すれ違いカウント正規化
- ペアの記録は `user_a < user_b` で正規化する（双方向関係を1行で管理）

#### FR-ENC-03 4回目すれ違い時の合意期限処理
- 4回目のすれ違いが発生した時点で、当該ペアに合意中の合意レコードがあり、まだ unlock されていない場合、当該合意は失効状態に遷移する

> ※ すれ違いを発火させる物理的な仕組み（BLE/GPS常時取得など）はMVP対象外。MVPでは外部から API を呼び出すシミュレーションで代替する。本番化フェーズで BLE 相互広告 + ネイティブモバイル実装に移行する。

### 6.3 段階的情報開示（FR-DIS）

#### FR-DIS-01 段階定義
| 段階 | 条件 | 開示情報 |
|---|---|---|
| Lv.0 | カウント = 1 | 段階情報のみ |
| Lv.1 | カウント = 2 | ニックネームの先頭1文字、ぼかしアイコン |
| Lv.2 | カウント ≥ 3 かつ未合意 | ニックネーム、アイコン、自己紹介サマリー |
| Lv.3 | 双方合意成立 | Lv.2 + 詳細プロフィール |

#### FR-DIS-02 自動開示と合意経由開示の区別
- Lv.0、Lv.1、Lv.2 はすれ違いカウントの累積で自動的に開示される
- Lv.3 は **自動開示されない**。双方の合意（§6.4）を経由してのみ開示される

#### FR-DIS-03 開示情報のサーバー側フィルタリング
- API は応答時点で、現在の段階に応じて開示情報を絞った形で返却する
- クライアント側で隠す方式ではなく、サーバー側で機密情報を返さない方式とする

### 6.4 相互合意による早期開示（FR-AGR）

#### FR-AGR-01 合意ボタン押下
- アプローチ解禁状態（カウント ≥ 3）のペアに対して、ユーザーは合意ボタンを押下できる
- 押下時刻が合意レコードに記録される

#### FR-AGR-02 合意成立条件
- ペアの両ユーザーが合意ボタンを押下した時点で、合意は成立し、Lv.3 が解放される
- 一方からの押下のみでは Lv.3 は解放されない

#### FR-AGR-03 合意期限切れ
- 4回目のすれ違いが発生した時点で合意未成立の場合、当該合意は失効する（§6.2 FR-ENC-03 参照）
- 失効後の合意ボタン押下は受け付けない

#### FR-AGR-04 合意状態の双方への通知
- 合意ボタン押下、合意成立、合意失効の各イベントは、サーバー送信イベント（SSE）により双方のクライアントに通知される

### 6.5 拠点保護（FR-HOM）

#### FR-HOM-01 自宅圏内除外
- すれ違い記録時、自分または相手の登録自宅から半径500m以内のすれ違いは記録しない
- 距離計算は Haversine 公式により実施する

#### FR-HOM-02 拠点登録の任意性
- 自宅登録はユーザーの任意とする
- 未登録の場合は拠点保護機能は適用されない

### 6.6 サイレントリジェクト（FR-REJ）

#### FR-REJ-01 リジェクト登録
- ユーザーは特定の相手に対してサイレントリジェクトを登録できる
- リジェクト関係は一方向（rejector → rejected）として保持する

#### FR-REJ-02 リジェクト後のカウント停止
- リジェクト関係がある場合、当該ペアのすれ違いは記録されない
- 既存のすれ違いカウントは保持されるが、ユーザーの相手リストには表示されない

#### FR-REJ-03 リジェクトの不可視性
- リジェクトされた側に通知や状態表示は行わない
- リジェクトされた側の画面からは、リジェクトしたユーザーが「単に最近すれ違っていない」と見える

### 6.7 通報（FR-RPT）

#### FR-RPT-01 通報受付
- ユーザーは特定の相手を通報できる
- 通報には任意の理由文を添付できる

#### FR-RPT-02 通報後の処理（MVPスコープ）
- 通報を受けたアカウントには警告マークを付与する（カウントリセットはMVPでは実施しない）
- 詳細な対応（複数通報による自動アカウント停止、運営確認フロー）は本番化フェーズで実装する

### 6.8 シェアカード生成（FR-SHR、本番化候補機能）

> ※ MVP では実装スコープ外（時間に余裕がある場合に追加）

#### FR-SHR-01 シェアカード生成
- Lv.3 解放後、ユーザーは双方のニックネーム頭文字、すれ違い回数、解放日時を含むシェアカード画像を生成できる
- カード画像にはサービスのロゴ・URLを含む（SNS拡散時の流入導線）

### 6.9 イエロー・サブマリン成長（FR-GROWTH）

すれ違い回数に応じて、相手ごとに「イエロー・サブマリン」のキャラクターが Lv.1 〜 Lv.5 に進化する。情報開示段階（FR-DIS）と完全に同期したペア単位の成長指標で、関係の積み重ねを可視化するデモ映え要素として位置付ける。

#### FR-GROWTH-01 レベル算出ロジック
- ペア単位のすれ違い回数 `count` に応じて、サブマリンレベルを算出する
- 算出式（`count` は 1 以上の整数）:

  | count | サブマリン Lv | 情報開示段階（参考） |
  |---|---|---|
  | 1 | Lv.1 | Lv.0（初対面） |
  | 2 | Lv.2 | Lv.1（ぼかし開示） |
  | 3 | Lv.3 | Lv.2（公的プロフィール開示） |
  | 4 | Lv.4 | Lv.3（合意で詳細解放） |
  | 5 以上 | Lv.5 | Lv.3（維持） |

- レベル判定はサーバー側で実施し、`GET /api/encounters` レスポンスの相手ごとに `submarine.level` と `submarine.imageUrl` を返す
- 状態の永続化は不要（`encounters.count` から派生する純粋関数）

#### FR-GROWTH-02 アセット
- レベル別画像（5段階）を `web/public/submarine/level{1..5}.png` に配置
- 元アセットは `app/image/イエロー・サブマリン_レベル{1..5}.png`（プロジェクトオーナー提供）

#### FR-GROWTH-03 表示
- すれ違い一覧画面: 各相手カードの先頭にサブマリン画像（56px）を表示
- すれ違い詳細画面: ヘッダー部に大きめのサブマリン画像（96px）と Lv. ラベルを表示
- レベルアップ時の演出は任意。MVP では既存の `encounter:updated` SSE 受信→画面再取得の流れに乗せる（専用イベントは追加しない）

#### FR-GROWTH-04 スコープ外
- アイテムによる成長加速（例: 博多ラーメン消費でレベルアップ）は本機能のスコープ外。シンプルに「すれ違い回数のみで進化」とする
- ユーザー単位の通算サブマリン（全ペア合計）は扱わない（あくまでペアごとの成長）

## 7. 非機能要件

### 7.1 性能要件
- API 応答時間: 平均 200ms 以下、95パーセンタイル 500ms 以下
- 同時接続ユーザー数: MVP では 100 ユーザー、α拡大期で 10,000 ユーザー
- SSE 接続維持: 25秒ごとに ping を送信し、コネクション切断を防止

### 7.2 可用性要件
- MVP: 単一インスタンス運用、可用性 SLO は設定しない
- 本番化: 月間稼働率 99.5% 以上を目標

### 7.3 拡張性要件
- 主要エンティティ（users、encounters、agreements）は将来のシャーディングを想定したスキーマ設計とする
- API は REST + SSE のシンプルな構成とし、将来的な GraphQL 等への移行余地を残す

### 7.4 互換性要件
- フロントエンドは PWA として実装し、iOS Safari 16+、Android Chrome 最新版で動作する
- スクリーンサイズは 320px 〜 1920px に対応する

### 7.5 アクセシビリティ要件
- WCAG 2.1 AA レベル準拠を目標
- フォーカスリング表示、aria-label 付与、`prefers-reduced-motion` 対応

### 7.6 国際化要件
- MVP は日本語のみ
- 本番化フェーズで英語・韓国語・繁体字中国語への対応を予定

┌─────────────────┐         ┌─────────────────┐

         │ HTTPS / SSE              │
         └──────────┬───────────────┘
                    ▼
         ┌──────────────────────┐
         │   API サーバー       │
         │  (Hono / Node.js)    │
         └──────────┬───────────┘
                    ▼
         ┌──────────────────────┐
         │     PostgreSQL       │
         └──────────────────────┘

### 8.2 採用技術スタック

| 領域 | 採用 | 備考 |
|---|---|---|
| フロントエンド | Next.js 14 (App Router) + TypeScript | PWA、Vercel デプロイ前提 |
| スタイル | Tailwind CSS | 静かなトーンの3色設計 |
| 状態管理 | Zustand | 軽量、合意状態のリアルタイム同期 |
| バックエンド | Hono (Node.js) | 軽量、ESM 対応 |
| 言語 | TypeScript | フロント・バック共通 |
| データベース | PostgreSQL 16 | UUID、トランザクション、行ロック |
| リアルタイム通信 | Server-Sent Events (SSE) | 合意ボタンの即時反映 |
| 認証（MVP） | 匿名セッション + ニックネーム | ハッカソンスコープ |
| 認証（本番化） | SMS認証 + 任意の顔認証 | 本番化フェーズで導入 |
| インフラ（MVP） | Vercel + Railway / Render | 即デプロイ系 |
| インフラ（本番化） | AWS / GCP（要選定） | スケーリング前提 |

### 8.3 技術選定の根拠
- ハッカソンの限られた時間内で動作するデモを優先
- 別担当者によるすれ違い検出 UI（マップ画面）と疎結合になるよう、API は明確に分離
- 本番化フェーズではネイティブモバイルへ移行することを前提とした基盤設計

## 9. データモデル

### 9.1 主要エンティティ

#### users
| カラム | 型 | 制約 |
|---|---|---|
| id | UUID | PRIMARY KEY |
| nickname | TEXT | NOT NULL |
| icon_url | TEXT | NULL 可 |
| profile_summary | TEXT | NULL 可 |
| profile_detail | TEXT | NULL 可 |
| home_lat | NUMERIC(9,6) | NULL 可 |
| home_lng | NUMERIC(9,6) | NULL 可 |
| created_at | TIMESTAMPTZ | NOT NULL |

#### encounters
| カラム | 型 | 制約 |
|---|---|---|
| id | UUID | PRIMARY KEY |
| user_a_id | UUID | NOT NULL, FK→users, CHECK (user_a_id < user_b_id) |
| user_b_id | UUID | NOT NULL, FK→users |
| count | INTEGER | NOT NULL, DEFAULT 1 |
| last_encountered_at | TIMESTAMPTZ | NOT NULL |
| last_counted_date | DATE | NOT NULL |
| created_at | TIMESTAMPTZ | NOT NULL |

UNIQUE (user_a_id, user_b_id)

#### agreements
| カラム | 型 | 制約 |
|---|---|---|
| id | UUID | PRIMARY KEY |
| encounter_id | UUID | NOT NULL, FK→encounters, UNIQUE |
| user_a_agreed_at | TIMESTAMPTZ | NULL 可 |
| user_b_agreed_at | TIMESTAMPTZ | NULL 可 |
| unlocked_at | TIMESTAMPTZ | NULL 可 |
| expired_at | TIMESTAMPTZ | NULL 可 |
| created_at | TIMESTAMPTZ | NOT NULL |

#### silent_rejects
| カラム | 型 | 制約 |
|---|---|---|
| id | UUID | PRIMARY KEY |
| rejector_id | UUID | NOT NULL, FK→users |
| rejected_id | UUID | NOT NULL, FK→users |
| created_at | TIMESTAMPTZ | NOT NULL |

UNIQUE (rejector_id, rejected_id)

#### reports
| カラム | 型 | 制約 |
|---|---|---|
| id | UUID | PRIMARY KEY |
| reporter_id | UUID | NOT NULL, FK→users |
| reported_id | UUID | NOT NULL, FK→users |
| reason | TEXT | NULL 可 |
| created_at | TIMESTAMPTZ | NOT NULL |

### 9.2 設計上の重要事項
- **`encounters` テーブルは `user_a_id < user_b_id` で正規化** することで、双方向関係を1行で管理する。CHECK 制約で逸脱を防止
- **同日丸めは `last_counted_date` カラム**で実現。同日中の追加発生はカウントしない
- **`agreements` の状態遷移**: `(両者 NULL) → 片側のみ → 両者あり (unlocked_at セット)` または `expired_at セット`
- **トランザクション**: encounter 更新と agreement 期限切れ判定は同一トランザクション内で実行し、レース条件を回避

## 12. UI/UX 要件

### 12.1 デザイン原則
1. **静寂のトーン**: 派手な色・通知連打を排除し、内向型ペルソナに適合する
2. **観察非対称を作らない**: 場所・時刻情報を画面に表示しない
3. **合意の重み**: 合意ボタンは契約のような重みを物理的に表現する（長押し2秒等）
4. **静かな離脱**: サイレントリジェクトの導線は控えめだが必ず発見可能
5. **余白の活用**: 1画面1要素を意識し、情報密度を抑える

### 12.2 カラーパレット
| 役割 | カラー | 用途 |
|---|---|---|
| ink | #1f2024 | 主要テキスト、強調 |
| ink-soft | #3a3b40 | 副次テキスト |
| ink-mute | #7a7b80 | 補助情報 |
| paper | #fafaf7 | 背景 |
| paper-card | #ffffff | カード背景 |
| accent | #6b7a8f | リンク・アクション・解放表現 |

### 12.3 タイポグラフィ
- フォント: system-ui ベース（OS の見慣れたフォントで安心感）
- 見出し: 太字、ウェイト 500、大きめのライン高
- 本文: 通常ウェイト、ライン高 1.6 以上

### 12.4 主要演出仕様

#### 合意ボタン（推奨実装）
- 長押し2秒で押下確定
- 押し始めにボタンが0.95倍に縮小
- 完了時に波紋アニメーション + バイブレーション（モバイル）

#### 詳細解放演出
- 詳細プロフィールエリアが上から1行ずつフェードイン（1.0秒）
- フルスクリーン演出は5秒間表示し、3秒目で「✦」のキーが画面を横切る
- `prefers-reduced-motion` 設定時はフェードのみに簡略化

### 12.5 モバイル対応必須項目
- iPhone Safari セーフエリア対応（`env(safe-area-inset-*)`）
- `100dvh` を使った高さ指定
- iOS のアドレスバー伸縮による要素隠れ対策
- 横画面・縦画面両対応
- iOS アクセシビリティ「特大文字」設定への対応

## 13. プライバシー・セキュリティ要件

### 13.1 プライバシー設計の原則
1. **最小収集の原則**: 業務に必要な最小限の情報のみ収集する
2. **観察非対称排除の原則**: 一方が他方を一方的に蓄積観察できない構造とする
3. **明示的同意の原則**: 詳細プロフィール開示は両者の明示的合意を要件とする
4. **削除権の保障**: ユーザーは自身のデータを削除できる（本番化フェーズで API 実装）

### 13.2 位置情報の取扱い
- 位置情報は **すれ違い判定の瞬間にのみ** 使用する
- 位置情報の **生データはサーバーに永続化しない**
- 自宅座標は機微情報として、登録は任意とする
- すれ違いの場所・時刻はユーザーに表示しない

### 13.3 認証・セッション管理
- MVP: 匿名セッション（クライアント側で UUID 保持）
- 本番化フェーズ: SMS認証 + 任意の顔認証
- セッショントークンは HttpOnly Cookie + CSRF 対策で保護

### 13.4 通信
- 全通信を HTTPS で暗号化
- API 認証は `X-User-Id` ヘッダー（MVP）。本番化では JWT / Session Token に移行

### 13.5 データ保護
- 個人情報を含むカラム（profile_detail 等）への暗号化は本番化で導入検討
- バックアップは1日1回、保管期間は法令と利用規約に従う
